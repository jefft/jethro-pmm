# SMS Database Tables

Schema source: `upgrades/2026-upgrade-to-2.40-sms.sql` (SMS tables) and
`upgrades/2026-upgrade-to-2.40.sql` (main schema). All tables and columns
are defined there. This page documents the semantics that aren't obvious from
column names alone.

**Key relationships** (FK columns versus diagram lines):

- `sms.sender` → `_person.id` (nullable: NULL for script sends)
- `_smsdelivery.sms_id` → `sms.id`: one send produces one delivery row per recipient (CASCADE delete)
- `_smsdelivery.personid` → `_person.id` (nullable: NULL if raw mobile number)
- `sms_note.(personid, id)` → `person_note.(personid, id)`: the note lives in the `person_note` / `_abstract_note` system
- `sms_note.smsdelivery_id` → `_smsdelivery.id`: a delivery may have zero or one linked notes (CASCADE delete)
- `person_note.id` → `_abstract_note.id`
- `sms_registered_sender.personid` → `_person.id`: the person a sender number is verified for. A number belongs to the first person verified for it; `DbLoggingSmsProvider::verifySenderNumber()` reads it before asking the provider, and claims an unowned number when the provider reports it verified


All FK relationships reference `_person`, never `person` (MySQL cannot create
foreign keys against views — see below).

## Cost tracking

Each `smsdelivery` row records what that delivery cost, at the time it was sent:

| Column | Meaning | Set from |
|---|---|---|
| `segments_used` | SMS segments charged, i.e. SMS against the provider balance (one credit is one SMS segment) | 5CentSMS `credits`; Cellcast `smsDetail.smscount`. NULL when the provider doesn't report it (SMS Broadcast, v4/template, rows logged before 2.40's cost tracking) |
| `per_segment_cost` | Dollars per segment | Cellcast `smsDetail.costpersms` (or `deductibleCredit / smscount`); otherwise `SMS_SEGMENT_COST` if set, else the sending provider's `SEGMENT_COST_MILLICENTS` default |
| `cost_bearer` | Whether this row bears the charge for its (possibly shared) message | `DeduplicatingSmsProvider` via the send — TRUE on a group's primary row, FALSE on the secondary persons sharing the number |

Both cost columns are written by the send (`logSms()`), by status polls (`DbLoggingSmsProvider`, only overwriting with values the provider actually reported) and by Synchronize History.

**Shared mobile numbers.** When several recipients share one number, one gateway message serves the whole group: all their `smsdelivery` rows share the group's `remote_id`, the primary row carries the reported `segments_used` (and `cost_bearer` 1), and each secondary row records `segments_used` 0 / `cost_bearer` 0 — so a message is counted once whether it went to one person or five sharing a handset. Status polls guard their cost update with `IF(cost_bearer, …)` so the provider's count is never copied onto a secondary's zero row. `sms_usage_daily` and `Sms::costSqlExpr()` count an explicit 0 as 0 (only NULL counts as 1).

The Messages page's Cost column (`Sms::costSqlExpr()`) sums `segments_used × per_segment_cost` over accepted deliveries, treating an unknown `segments_used` as 1 and an unknown `per_segment_cost` as the default of **the provider recorded on that row** (`\Jethro\Sms\defaultSegmentCost()`). Prices are fixed per row, so changing `SMS_SEGMENT_COST` or switching providers only affects new sends.

## Jethro Views and the `_`-prefixed Tables

Jethro uses MySQL views to enforce row-level security. Every queryable entity
has two names: the **`_`-prefixed base table** (the physical storage) and the
**view** (the security-filtered access path). Foreign keys always reference
the base table.

| View | Base table | Filter |
|---|---|---|
| `person` | `_person` | Current user's congregation + group restrictions via `getCurrentUserID()` |
| `person_group` | `_person_group` | Group restrictions via `getCurrentUserID()` |
| `member` | `_person` + `_family` | Flattened join; visible only when the current user shares a member-sharing group with the person |
| `abstract_note` | `_abstract_note` | Assignee is current user AND status is 'pending', OR user has permission bits 48 |
| `smsdelivery` | `_smsdelivery` | Deliveries to persons visible through `person`, plus those with no person (raw numbers) |

The views use `getCurrentUserID()`, a MySQL stored function that returns the
session variable `@current_user_id`. In CLI/testing contexts, set it before
querying through views:

```sql
SET @current_user_id = 1;
SELECT * FROM person WHERE id = 42;
```

Without this, views return empty results (the function sees NULL, and no row
matches `NULL = …`).

### Why `_person` not `person` in FKs?

MySQL does not allow foreign keys to reference views — only base tables. So
`sms.sender REFERENCES _person(id)` and `_smsdelivery.personid REFERENCES
_person(id)`, and `sms_note.smsdelivery_id` references `_smsdelivery(id)`.
This is correct: the FK ensures referential integrity at the storage level;
the view layer adds security on top.

### Which name to use for SMS deliveries

Pages and calls read **`smsdelivery`**, so restricted accounts only ever see
deliveries to persons they may see (Persons → Messages, the person Messages
tab, `?call=sms_info`, notes, the `Sms` aggregates — a send with no visible
delivery isn't listed, and its counts and cost cover visible deliveries only).
Writers and system-level code use **`_smsdelivery`**: logging a send
(`insertSms`), status caching (`DbLoggingSmsProvider`), Synchronize History,
cancel (`cancelSms`, already permission-checked: a sender's cancel reaches all
their recipients), CLI export and the legacy-note migration. Several of these
run with no current user, when the view would be empty. `SmsDelivery`
(`db_objects/smsdelivery.class.php`) inserts into `_smsdelivery`. The view is
`SELECT sd.*`, expanded when created: recreate it after adding columns.

### Legacy SMS notes

Before 2.40, each SMS send created a `person_note` + `_abstract_note` row
(subject `'SMS Sent'`). The `2026-upgrade-to-2.40-sms.sql` migration converts
these into `sms` + `smsdelivery` rows and removes the old note records.

### Global search ("messages")

`View__Mixed_Search::searchMessages()` (`views/view_0_mixed_search.class.php`)
matches `COALESCE(smsdelivery.body, sms.body) LIKE %search%` for non-bulk sends
only: those with exactly one row in `_smsdelivery` (bulk-ness counts every
delivery). Rows are read through the restricted `smsdelivery` view. Offered only
when the `SMS` feature is enabled and the user has `PERM_VIEWSMS`; searchtype `m`.
