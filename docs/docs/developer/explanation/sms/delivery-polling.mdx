# Delivery Polling

Delivery status polling is how Jethro tracks whether messages reached the recipient's handset.

## The Problem

SMS gateways are asynchronous — a message is accepted (status: Queued), dispatched (status: Sent), and eventually delivered (status: Delivered) or failed. The time between "Sent" and "Delivered" can be seconds or hours. Jethro needs to show the final status.

## The Solution: Client-Side Polling

Rather than a server-side cron job, Jethro polls from the page with **Datastar**.

### Why Client-Side?

- **Simplicity** — no cron setup, no background worker
- **Lazy** — polls only when someone actually views a messages page
- **Self-limiting** — intervals back off with age; polling stops 24h after the send time
- **Self-cleaning** — a span stops polling once its delivery reaches a final status

### How It Works

1. The status renderers (`renderSmsDeliveryStatusIndicator()` on a person's Messages tab, `renderSmsDeliveryStatusIcon()` on Persons → Messages) emit a polling span for every delivery that is not final (`SmsStatus::isFinal()`) — **including 'sent'**, since delivery confirmation or a late failure arrives after the gateway accepts the message — while its provider is the configured one and it is under 24h (`STATUS_POLL_WINDOW_SECS`) past its send time
2. The span fires `?call=sms_info&id=N` on a backoff interval (`smsDeliveryPollIntervalSecs()`), and once on render when past its send time
3. `Call_SMS_Info` asks the provider (one `listRecentDeliveries()` call over the polling window) and returns updated status HTML
4. If status is now final, the span updates and stops polling
5. If still non-final, the span re-renders with a fresh interval

## Caching

`DbLoggingSmsProvider` stores the raw gateway response in `smsdelivery.raw_response`. When a final status is found (delivered or failed), subsequent polls skip the API call entirely — the cached response is returned instantly.

## Cancel Links

For scheduled messages, the polling response includes a Cancel link. This appears in the UI only after the first poll returns — it's not rendered in the initial page to avoid showing cancel links for messages that might have already been sent by the time the page loads.

## Provider Support

| Provider | Supports Polling |
|---|---|
| FiveCentSms v5 | ✓ via GET endpoint |
| MobileMessage | ✓ via GET endpoint |
| EJSms | ✓ (extends v5) |
| FiveCentSms v4 | ✗ — no polling endpoint |

## Limitations

- Only polls when a messages page is open (not a true background process)
- Deliveries still not final 24h after their send time are never re-checked
- Browser must remain open for polling to continue
