#### Restricted database accounts: re-grant on the renamed tables

If `conf.php` sets `DB_MEMBERS_USERNAME` or `DB_PUBLIC_USERNAME` to a separate
MySQL account that is allowed only the tables each area needs (see
[Database accounts](../administration/config/index.mdx#database-accounts-optional)),
2.40 renames two tables that Jethro writes to. `family` and
`custom_field_value` are now read-only views, and the writers point at the
renamed base tables `_family` and `_custom_field_value`. Grants for the old
table names do not follow the rename: after upgrading, a members-area account
can no longer save family details, and fails with
`ERROR 1142 (42000): UPDATE command denied ... '_family'`.

Give the members-area account the new write tables (its database-wide `SELECT`
covers the read views):

```sql
GRANT SELECT ON `jethro`.* TO 'site_members'@'localhost';
GRANT UPDATE ON `jethro`.`_family` TO 'site_members'@'localhost';
GRANT INSERT, UPDATE, DELETE ON `jethro`.`_custom_field_value` TO 'site_members'@'localhost';
GRANT INSERT, UPDATE, DELETE ON `jethro`.`db_object_lock` TO 'site_members'@'localhost';
```

Substitute your database name and account names. `_person` and `db_object_lock`
kept their 2.39 names, so existing grants on them still apply. The public area
is read-only and the views kept their names, so a `DB_PUBLIC_USERNAME` account
with `SELECT` on the database needs no change. Check the result with
`SHOW GRANTS FOR 'site_members'@'localhost';`: it must include `_family` and
`_custom_field_value`.
